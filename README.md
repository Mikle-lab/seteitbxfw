# XLM Radar v0.1

Инструмент наблюдения за обнаруженными крупными держателями XLM в Stellar Mainnet. Сбор данных выполняет GitHub Actions. Статический интерфейс работает на GitHub Pages. Ключи и коммерческие сервисы проекту не нужны.

## Запуск и публикация

```sh
python3 -m unittest discover -s tests -v
python3 -m collector.scan
python3 -m collector.export
python3 -m http.server 3000 --directory dist
```

В GitHub откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**. Рабочий процесс **XLM Radar** доступен на вкладке **Actions**, запускается вручную через **Run workflow** и по расписанию каждые 6 минут. GitHub может задерживать или пропускать отдельные запуски. Расписание действует на ветке по умолчанию `main`. Сборщик обрабатывает ограниченный пакет страниц, сохраняет отставание и догружает оставшиеся страницы при следующем запуске. Публикация не требует открытого сайта. GitHub может приостановить расписание публичного репозитория при длительной неактивности.

## Что означают показатели

- Начальное покрытие начинается с недавнего окна, заданного в `config.json`. Кандидаты выявляются по известным XLM-движениям от 1 000 XLM и источникам отдельных операций, меняющих балансы. Текущие остатки запрашиваются у Horizon. Известные держатели обновляются по очереди. В обзоре показываются снимки, которые могут быть получены в разное время. Переходы между порогами фиксируются при следующем наблюдении.
- Накопление и сокращение считаются по изменениям между снимками внутри периода. Первое наблюдение исключается из изменения. Полученные и отправленные суммы в таблицах относятся к сохранённым крупным движениям, а не ко всем переводам счёта. Объём маршрутизированного платежа показан отдельно для каждого доступного XLM-края маршрута.
- Сигналы v0.1 включают крупные XLM-движения, обнаружение кита, резкое изменение баланса, повышение категории и выход из категории китов. Адреса контрагентов не объединяются по предполагаемому владельцу.
- Порог крупного движения, порог кита, категории, квоты и реестр подтверждённых меток задаются в `config.json`. Метка должна содержать `name`, `type`, `source` и `confidence`. v0.1 не публикует биржевые потоки, покупки и продажи или резервы без отдельной проверенной аналитики.
- История доступна с запуска сборщика. Проект не индексирует все аккаунты Stellar и не восстанавливает пропуски, вышедшие за период хранения Horizon. При таком пропуске сборщик остановится и запишет ошибку вместо автоматического перескока курсора. Комиссии, детали биржевых сделок и все движения в пулах не реконструируются из отдельных строк операций.

## Хранение и интерфейсы

`data/state.json` хранит версию схемы, курсор операций, очередь кандидатов, текущие балансы и состояние сканирования. `data/archive/YYYY-MM-DD.json` содержит словари событий по стабильным идентификаторам. `data/errors/` хранит ошибки отдельно от успешных контрольных точек. Журнал `pending.json` записывается первым, воспроизводится идемпотентно и удаляется после фиксации архива и состояния. GitHub Actions сериализует запуски, а локальный процесс дополнительно блокирует параллельную запись в тот же каталог.

`collector.export` формирует публичную схему 1: сводку, компактный индекс кошельков, отдельные карточки и страницы операций и сигналов по 250 записей. Браузер подгружает выбранную страницу и не скачивает архив целиком. Курсоры, очередь и технические ошибки в артефакт сайта не входят. Нарастающий архив следует контролировать перед достижением лимитов GitHub. Формат публичной выгрузки можно сохранить при переносе источника в БД.

Документация Stellar: [операции](https://developers.stellar.org/docs/data/apis/horizon/api-reference/list-all-operations), [аккаунты](https://developers.stellar.org/docs/data/apis/horizon/api-reference/resources/accounts/index), [Horizon](https://developers.stellar.org/docs/data/apis/horizon).
