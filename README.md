# XLM Radar v0.3

Инструмент наблюдения за обнаруженными крупными держателями XLM в Stellar Mainnet. Сбор данных выполняет GitHub Actions. Статический интерфейс работает на GitHub Pages. Ключи и коммерческие сервисы проекту не нужны.

## Запуск и публикация

```sh
python3 -m unittest discover -s tests -v
python3 -m collector.scan
python3 -m collector.export
python3 -m http.server 3000 --directory dist
```

В GitHub откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**. Рабочий процесс **XLM Radar** доступен на вкладке **Actions**, запускается вручную через **Run workflow** и по расписанию каждые 6 минут. GitHub может задерживать или пропускать отдельные запуски. Расписание действует на ветке по умолчанию `main`. Сборщик обрабатывает ограниченный пакет страниц, сохраняет отставание и догружает оставшиеся страницы при следующем запуске. Публикация не требует открытого сайта. GitHub может приостановить расписание публичного репозитория при длительной неактивности.

## Что означают показатели

- Начальное покрытие начинается с недавнего окна, заданного в `config.json`. Кандидаты выявляются по известным XLM-движениям от 1 000 XLM и источникам отдельных операций, меняющих балансы. Текущие остатки запрашиваются у Horizon. Известные держатели обновляются по очереди. В обзоре показываются снимки, которые могут быть получены в разное время. Переходы между порогами фиксируются при следующем наблюдении.
- Накопление и сокращение считаются по изменениям между снимками внутри периода. Первое наблюдение исключается из изменения. Полученные и отправленные суммы в таблицах относятся к сохранённым крупным движениям, а не ко всем переводам счёта. Объём маршрутизированного платежа показан отдельно для каждого доступного XLM-края маршрута.
- Сигналы v0.1 включают крупные XLM-движения, обнаружение кита, резкое изменение баланса, повышение категории и выход из категории китов. Адреса контрагентов не объединяются по предполагаемому владельцу.
- Порог крупного движения, порог кита, категории, квоты и реестр подтверждённых меток задаются в `config.json`. Метка должна содержать `name`, `type`, `source` и `confidence`. v0.1 не публикует биржевые потоки, покупки и продажи или резервы без отдельной проверенной аналитики.
- История доступна с запуска сборщика. Проект не индексирует все аккаунты Stellar и не восстанавливает пропуски, вышедшие за период хранения Horizon. При таком пропуске сборщик остановится и запишет ошибку вместо автоматического перескока курсора. Комиссии, детали биржевых сделок и все движения в пулах не реконструируются из отдельных строк операций.

## Хранение и интерфейсы

`data/state.json` хранит версию схемы, курсор операций, очередь кандидатов, текущие балансы и состояние сканирования. `data/archive/YYYY-MM-DD.json` содержит словари событий по стабильным идентификаторам. `data/errors/` хранит ошибки отдельно от успешных контрольных точек. Журнал `pending.json` записывается первым, воспроизводится идемпотентно и удаляется после фиксации архива и состояния. GitHub Actions сериализует запуски, а локальный процесс дополнительно блокирует параллельную запись в тот же каталог.

`collector.export` формирует публичную схему 1: сводку, компактный индекс кошельков, отдельные карточки и страницы операций и сигналов по 250 записей. Браузер подгружает выбранную страницу и не скачивает архив целиком. Курсоры, очередь и технические ошибки в артефакт сайта не входят. Нарастающий архив следует контролировать перед достижением лимитов GitHub. Формат публичной выгрузки можно сохранить при переносе источника в БД.

Лимит сборщика по умолчанию составляет 350 HTTP-запросов на запуск, включая повторные попытки. Horizon ограничивает запросы по IP; стандартная настройка сервера составляет 3 600 запросов в час и может меняться у оператора. При 429 сборщик учитывает Retry-After и увеличивает задержку повторов. [Лимиты Horizon](https://developers.stellar.org/docs/data/apis/horizon/api-reference/structure/rate-limiting)

Документация Stellar: [операции](https://developers.stellar.org/docs/data/apis/horizon/api-reference/list-all-operations), [аккаунты](https://developers.stellar.org/docs/data/apis/horizon/api-reference/resources/accounts/index), [Horizon](https://developers.stellar.org/docs/data/apis/horizon).

## Биржи и DEX (v0.2)

- Биржевой реестр содержит публично атрибутированные адреса Binance, Binance.US, Kraken и Coinbase. Уровень доверия и ссылка на источник доступны в таблице. Horizon подтверждает существование счёта и баланс. Метка из каталога StellarExpert имеет среднюю достоверность. Балансы этих адресов не представляют полные резервы биржи.
- Сборщик учитывает прямые успешные платежи XLM, пересекающие границу известного реестра. Перевод между двумя адресами реестра исключается из общего потока. Периоды до подключения модуля не покрыты.
- DEX использует [Horizon /trades](https://developers.stellar.org/docs/data/apis/horizon/api-reference/resources/trades/object) с отдельным курсором. Учитываются исполнения XLM в стакане и пулах. Покупка или продажа определяется для инициатора операции, когда его публичный адрес совпадает со стороной исполнения. Нераспознанные направления входят в объём отдельной строкой. Объём маршрута складывается из его отдельных исполнений с XLM.
- В архиве хранятся минутные суммы по паре и направлению и до 20 крупнейших исполнений за сканирование. Граница периода для сумм округляется вниз до минуты. Таблица крупнейших исполнений строится по сохранённым записям. Публичная схема 1 дополнена файлом `markets.json`.
- Soroban-свопы, отсутствующие в потоке Horizon Trades, не покрываются.

## Динамика и персональные сигналы (v0.3)

Раздел «Динамика» показывает рейтинги накопления и сокращения за 7 и 30 завершённых суток UTC. Дневное изменение определяется по двум последовательным закрытиям. Для закрытия используется последнее доступное наблюдение в пределах трёх часов до полуночи. Отсутствующие дни не считаются нулевыми. Рейтинг включает только адреса с полным покрытием окна и исключает помеченные кошельки. Карточка кошелька показывает и частичную историю с числом наблюдавшихся дней.

Статистический сигнал сравнивает дневное изменение с нижней медианой наблюдений за предшествующие 14 суток. Нужно не меньше семи дневных измерений. Для сигнала абсолютный размер движения и расстояние до медианы должны достичь настроенного порога (по умолчанию 25 000 XLM), а расстояние должно составить не меньше шести медианных абсолютных отклонений. Анализ завершённых суток запускается с 03:00 UTC. Сигнал и его контрольная дата сохраняются вместе с остальными данными сборщика.

Публичная схема 1 получила `trends.json`, поле `trends` в карточках кошельков и поля `last_trigger` и `scheduled` в сводке. `scheduled` обновляется только после успешного сбора с событием `schedule`.

### Наблюдаемая тишина и повторные переводы

В таблице китов и в карточке адреса видна длительность тишины. Она отсчитывается от последней замеченной операции или от даты обнаружения адреса, если она позднее. Правая граница определяется курсором просмотренных операций. Поэтому задержка сборщика не увеличивает показанный период. При первой замеченной операции после 30 суток тишины создаётся сигнал с устойчивым идентификатором. Порог задаётся параметром `inactive_days`. История до обнаружения и операции, в которых Horizon не позволяет однозначно определить участника, в оценку не входят.

Раздел «Переводы между китами» показывает прямые крупные платежи XLM за 30 дней между отслеживаемыми адресами без известных служебных меток. Для попадания в таблицу нужны минимум три отдельных транзакции в разные даты UTC (минимум два дня). В строке есть сумма и ссылки на примеры. Эти наблюдения описывают переводы, а принадлежность адресов требует самостоятельных доказательств.

Публичная схема 1 дополнена `interactions.json`, полем `inactivity` у адресов и списком `interactions` в карточках. Изменения совместимы с архивами предыдущих версий.

### Цена XLM/USD

«Динамика» показывает дневное закрытие XLM/USD по публичным котировкам Coinbase Exchange. Карточка кошелька сопоставляет изменение баланса и изменение цены по дате UTC. Текущая незавершённая свеча исключается. Дневное изменение цены рассчитывается при наличии закрытия предыдущей календарной даты. Ошибка ценового источника не останавливает сбор Stellar. Сборщик сохраняет котировки в дневных архивах и показывает последнюю доступную историю. [Документация Coinbase Exchange](https://docs.cdp.coinbase.com/api-reference/exchange-api/rest-api/products/get-product-candles)

### Telegram-уведомления

Чтобы включить уведомления, создайте бота через [BotFather](https://t.me/BotFather), откройте с ним чат и нажмите Start. Для канала добавьте бота с правом публиковать сообщения. В [GitHub → Settings → Secrets and variables → Actions](https://github.com/Mikle-lab/seteitbxfw/settings/secrets/actions) создайте два **Repository secrets**: `TELEGRAM_BOT_TOKEN` для токена бота и `TELEGRAM_CHAT_ID` для числового ID чата или имени публичного канала в формате `@channel`. Для частного чата ID доступен в поле `message.chat.id` ответа официального метода [getUpdates](https://core.telegram.org/bots/api#getupdates) после сообщения боту. Веб-сайт и журнал Actions этих значений не получают.

Первый успешный запуск с двумя секретами фиксирует начало доставки. Далее после успешной публикации отправляется до восьми важных сигналов за запуск, начиная с самого раннего недоставленного. Включены высокая и критическая значимость. Срок повторной попытки составляет два дня. Подтверждённые сигналы сохраняются в `data/notifications.json` по идентификаторам, без токена и ID чата. При разрыве связи после приёма сообщения Telegram или до сохранения контрольной точки возможна повторная доставка.

### Резервный запуск

В ручном запуске workflow **XLM Radar** доступен параметр `only_if_stale`. При включённом параметре запуск пропускает сбор и развёртывание, если последнее сканирование успешно завершилось менее 15 минут назад. При устаревших данных он запускает тот же сборщик. Если будет подключён независимый планировщик, его авторизованный вызов может использовать команду:

```sh
gh workflow run radar.yml -R Mikle-lab/seteitbxfw --ref main -f only_if_stale=true
```

GitHub-разрешение на запуск workflow хранится на стороне планировщика. В публичном JavaScript токена нет. В сводке поля `scheduled` и `fallback` обновляются раздельно по фактическим успешным запускам.

### Автоматическое продолжение сбора

Workflow **XLM Radar** поддерживает цепочку автоматических сборов с шестиминутным шагом. Первый запуск принимает Unix-время в секундах в поле `auto_at`. Задание `continue-schedule` вызывает следующий запуск с помощью встроенного токена GitHub Actions. Временные интервалы отсчитываются от первого слота. Просроченные слоты пропускаются. GitHub может задерживать очередь и выполнение. Штатное cron-расписание сохраняется. Для обоих автоматических источников действует проверка четырёхминутной свежести, чтобы не повторять сбор. При отставании учитывается время последней просмотренной операции.

Остановить цепочку можно отменой её активного запуска или установкой переменной репозитория `RADAR_AUTORUN=off`. После отмены проверьте в Actions, не успел ли уже встать в очередь следующий запуск. Для перезапуска уберите `off` и вручную запустите workflow с текущим Unix-временем в `auto_at`. GitHub может прервать цепочку при сбое задания таймера или отмене запуска. Сводка помечает успешный сбор этой цепочки полем `automatic`.
